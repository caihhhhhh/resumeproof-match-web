# ResumeProof Match 第一性原理产品审计

审计日期：2026-09-07

## 用户真正要完成的任务

用户不是来获得一个分数，而是要在尽可能短的时间内完成三个决定：

1. 这个岗位是否值得投递；
2. 自己有哪些真实证据能够支撑岗位要求；
3. 应该采用哪些修改，并导出一份可以投递的简历。

核心北极星指标应是“首次获得可信投递决定的时间”，而不是页面浏览量或分析次数。

## 核心流程健康度

1. 首页定位 — 健康：价值主张清晰，主次 CTA 明确，视觉识别统一。
2. 材料输入 — 基本健康：上传、粘贴、URL、OCR 与示例入口齐全；首屏信息量较大，分析按钮在常见桌面视口下需要滚动后才能看到。
3. 匹配结果 — 基本健康：有分数、结论、关键差距、权重和证据核验；总分仍然过于显眼，容易被理解为确定性结论。
4. 逐项证据 — 健康：能够回到简历原句，并解释判断依据，这是当前产品最强的可信度资产。
5. 建议决策 — 健康：保留原文、建议版本、修改原因和预期作用，用户可采用、修改或跳过。
6. 全文审核与导出 — 基本健康：结构化编辑、实时预览、模板和多格式导出已形成闭环；编辑区仍偏密，PDF 依赖系统打印，跨浏览器成品一致性不足。

## 优先级建议

### P0：先增强决策可信度与输出确定性

- 将硬条件从普通要求中独立出来，完整核对地点、签证、学历、年限、语言、行业等门槛；任何未确认硬条件都不得被总分掩盖。
- 弱化单一总分，首页结论改为“立即投递 / 补证后投递 / 暂不建议”，同时说明决定由哪些证据和未确认项产生。
- 在人工编辑后再做一次事实差异检查，标出新增数字、工具、公司、日期和成果，防止用户修改时引入无证据信息。
- 改为稳定的服务端 PDF 生成，并加入可选择文字、字体嵌入、页边距、分页和 ATS 基础检查。

### P1：把一次性工具变成可复用工作台

- 支持可选的本地保存与恢复：保存一份基础简历、多个 JD 和对应版本；默认仍不上传长期保存。
- 增加岗位工作区：岗位状态、匹配结论、使用的简历版本、投递日期和后续结果放在同一记录中。
- 支持多岗位横向比较，帮助用户判断同一份经历更适合哪些职位，而不只是重复跑单次分析。
- 输出页增加明确的下一步：补哪条证据、改哪段简历、是否值得投递，而不只停在报告阅读。

### P2：建立真实结果反馈闭环

- 在用户自愿的前提下记录投递、筛选、面试和录用结果，以结果校准匹配方法。
- 建立个人证据库：经用户确认的项目、指标和原句可以复用到不同岗位，但任何迁移都需再次审核。
- 基于已确认差距生成面试准备材料；不要在核心匹配闭环稳定前继续增加泛化写作工具。

## 数据与 GA4

现有事件已经覆盖上传、JD 解析、分析、建议采用、审核和导出，基础较完整。下一步不应继续堆事件名，而应固定四层漏斗：

1. 激活：看到至少一条可核验的岗位要求与简历证据；
2. 获得价值：采用或修改至少一条建议；
3. 完成：确认全文并导出；
4. 留存：7 天内使用同一基础简历匹配第二个岗位。

后台重点增加：各步骤转化率、JD 解析成功率、OCR 成功率、AI 分析 P50/P95 耗时、失败原因、建议采用率、导出率、渠道完成率。继续禁止向 GA4 发送简历正文、JD 正文、文件名、公司或职位名称。

## 设计与可访问性风险

- 材料页和结果页的辅助文字偏小且颜色较浅，长页面阅读负担较高。
- 审核页左侧编辑区控件密集，建议增加吸顶分区导航、预览缩放和只显示当前模块的聚焦模式。
- 本次只检查了桌面流程；尚未完成手机、键盘导航、200% 缩放和屏幕阅读器验证，因此不能据此声称符合 WCAG。

## 推荐进化顺序

先做“硬条件核验 + 事实差异检查 + 稳定 PDF”，再做“基础简历与岗位版本工作台”，最后才做“结果反馈与个性化”。这样每一阶段都直接缩短用户从材料到可信投递决定的时间，不会把产品做成臃肿的求职工具箱。
